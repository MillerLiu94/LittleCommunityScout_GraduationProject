# 社區小尖兵 AI Agent 回覆速度測試報告

> 測試日期：2026-11-02（`bench_agent.py` 01:24～01:58；串流與日誌診斷 02:10）
> 測試端點：`POST /api/chat`（非串流）
> Agent 模型：Ollama `qwen3.8-16k:latest`（qwen3.8:27b 的 16k 版本）

---

## 0. 重點摘要

- **測試規模**：120 個請求（DB 組 100 次、Web 組 20 次），全部成功，沒有失敗或逾時；`thread_id` 123 個（含暖機）全部不重複；整輪約 33.7 分鐘。
- **平均耗時**：DB 組 15.55 秒（中位數 13.65 秒）、Web 組 23.42 秒（中位數 21.54 秒）；最快 8.37 秒、最慢 44.64 秒。
- **網路與 SQL 都不是瓶頸**：不經 AI 的 `/api/categories` 中位數只有 15 毫秒；對一次完整請求（DB07）的日誌拆解顯示，5 條 SQL 加起來約 12 毫秒，8 次模型呼叫占 98% 以上；其中生成 token 約占 70%、讀取提示約占 18%、模型載入與其他約占 12%。
- **固定成本約 8～11 秒**：最簡單的計數題（回覆只有 21～58 字）也要 8.7～10.9 秒；最慢的是 DB07（30.27 秒）、DB06（28.48 秒）、DB08（25.04 秒）和 WEB09（44.64 秒）。
- **思考模式確實開著**：最終答案那次呼叫的第一個字比預期晚約 4.65 秒（約 186 個 token 沒有顯示）。Modelfile 無法關閉思考，**只能在呼叫時設定**（第 4.6、6.7 節）。
- **agent 的做法有可優化的地方**（第 5、6 節）：每次都先查資料表欄位並猜錯欄位名稱、SQL 一次回傳整包資料、多餘的確認查詢、最終答案偏長、supervisor 路由輸出偏長。
- **三個資源風險**：閒置後重載模型會多花約 3.3 秒；模型架構不支援並行請求（多人同時問會排隊）；GPU 記憶體餘裕只有約 1 GiB（第 4.7 節與 P11～P13）。
- **答案正確性**：DB13（事件草稿各狀態筆數）的答案可能不正確，與 DB14 的結果互相矛盾（第 3.2 節）。

## 2. 測試方法

### 2.1 測試設計

| 項目 | 設定 |
| --- | --- |
| 工具 | `bench_agent.py`（自製），每個請求送出 `{"message": 題目, "thread_id": 全新 id}` |
| DB 組 | 20 種題型 × 5 次 = 100 次，目標只派給 DB_Expert，不花 Tavily 額度 |
| Web 組 | 20 題 × 1 次 = 20 次，目標只派給 Researcher；每題只跑一次是為了節省 Tavily 額度 |
| 排程 | 120 個請求用固定亂數種子（42）打散，Web 題平均散佈（約每 6 個請求出現 1 次） |
| thread_id | 格式 `bench_{執行時間}_{組別}_{序號}_{隨機碼}`，程式內檢查不重複；實際 123 個（含暖機）全部不重複 |
| 暖機 | 正式計時前 3 次（使用 DB01、DB12、DB11，不花 Tavily 額度），結果另外記錄 |
| 對照組 | 測試前、後各 20 次 `GET /api/categories`（不經 AI），量網路與伺服器固定開銷 |
| 執行方式 | 一次一個請求（不並發）；逾時 180 秒；失敗不重試，如實記錄 |

### 2.2 量測方式與統計定義

- **耗時**：用 `time.perf_counter()` 量「送出請求到收到完整回覆」的客戶端時間，連線使用 `requests.Session`（保持連線）。
- **成功**：HTTP 200 且 `reply` 非空。耗時統計只計入成功的請求，失敗另外列出。
- **平均 / 中位數**：平均容易被少數極慢的請求拉高，中位數代表「一半的請求比它快」。
- **標準差**：每次耗時離平均有多遠，越小越穩定。
- **P90 / P95**：90% / 95% 的請求都比這個時間快；樣本少於 30 時僅供參考（接近最大值）。
- **平均字/秒**：每筆「回覆字數 ÷ 耗時」的平均，是端到端的有效產出速度，不是模型的生成速度。

### 2.3 補充診斷方法

| 方法 | 用途 |
| --- | --- |
| `stream_probe.py` | 用 `/api/chat/stream` 記錄每個 SSE 事件抵達時間，估算路由、專家決策、工具＋首字、輸出、收尾各階段 |
| PostgreSQL 日誌 | `log_min_duration_statement = 0`，記錄每條 SQL 與耗時 |
| Ollama 日誌 | `journalctl -u ollama`，看每次模型呼叫的提示 token 數、輸出 token 數與耗時 |

### 3.2 補充分析

**穩定性與冷啟動**

- 沒有明顯漂移：DB 組前半平均 15.47 秒、後半 15.64 秒；Web 組 22.71 / 24.13 秒。
- 同一題的耗時很穩定：20 個 DB 題中有 18 題的變異係數（標準差 ÷ 平均）低於 10%，只有 DB19（24%）與 DB06（22%）超過 10%。
- 冷啟動：第一筆暖機（DB01）12.52 秒、正式測試 DB01 平均 8.70 秒，多約 3.8 秒；02:10 的日誌直接看到模型重載花了 2.81 秒（見 4.2 節）。
- DB06 呈現兩種耗時：5 次中 1 次 17.42 秒，其餘 4 次 30.55～31.81 秒，答案內容相同。原因無法從這份資料判斷。

**DB 組的耗時與題型（每題平均）**

| 類型 | 題目（平均耗時） | 範圍 |
| --- | --- | --- |
| 單一數字（計數） | DB01（8.70 s）、DB10（10.37 s）、DB11（10.37 s）、DB02（10.88 s） | 約 8.7～10.9 s |
| 小型統計、聚合 | DB04（10.41 s）、DB16（11.63 s）、DB13（12.36 s）、DB17（12.83 s）、DB03（14.47 s）、DB18（14.80 s） | 約 10～15 s |
| 取單筆或欄位 | DB15（12.16 s）、DB05（13.83 s）、DB12（15.44 s）、DB14（17.92 s） | 約 12～18 s |
| 查無資料 / 彙整 | DB19（15.86 s）、DB20（17.18 s） | 約 16～17 s |
| 需要時間換算 | DB09（18.06 s）、DB06（28.48 s） | 約 18～28 s |
| 大量列資料 | DB08（25.04 s）、DB07（30.27 s） | 約 25～30 s |

- 回覆字數與耗時相關（DB 相關係數 0.62、Web 0.73；粗略關係 DB「耗時 ≈ 11.3 秒 ＋ 0.035 秒 × 字數」、Web「≈ 6.4 秒 ＋ 0.049 秒 × 字數」）。但這不能解讀成「輸出字數是主因」：這個斜率相當於每秒只多出約 20～29 個字，複雜問題既需要更多處理步驟、回覆也比較長，兩者同時變大。截距（約 11 秒、6 秒）只是回歸的粗略估計。
- 回覆只有 21～58 字的計數題仍然要 8.7～10.9 秒，代表有一段與答案長短無關的固定成本。

**Web 組**

- 範圍 15.58～44.64 秒，變異係數約 30%。最快的是 WEB02（15.58 s）、WEB01（16.22 s）、WEB12（16.84 s）；最慢的是 WEB09（44.64 s，福利補助）、WEB16（35.51 s，病媒蚊資源）、WEB17（32.30 s，近期活動）。偏向「有哪些資源、近期活動」的題目比「要通報哪個單位」的題目慢，但每題只有 1 次，這只是觀察，不是結論。
- 抽查回覆內容，Web 題都有引用外部資訊（公告、官網、1999 專線等），沒有看到被誤派去查資料庫的跡象。

**回覆內容的穩定性與正確性（非速度問題，但值得注意）**

- 20 個 DB 題中，五次回覆完全相同的有 3 題；其餘題目措辭每次不同（2 種不同回覆 6 題、3 種 6 題、4 種 4 題、5 種 1 題）。單純計數題的數字一致（66 筆案件全部 pending、51 筆附圖、5 位使用者、平均每人 13.2 件）。Ollama 日誌顯示請求的取樣是貪婪解碼（`temp = 0.000`），措辭仍會變動的原因無法從這份資料判斷。
- **DB14（事件草稿缺少地點）**五次都回答「1 筆」，並提到那筆的狀態是「等待補上位置」、地址與經緯度是空的，看起來確實查到了事件草稿。
- **DB13（事件草稿各狀態有幾筆）可能不正確**：五次都回答「只有 pending 一種狀態、共 66 筆」，這個數字與案件總數相同，而且與 DB14 提到的「等待補上位置」狀態互相矛盾，所以 DB13 很可能是在 `cases` 表而不是 `event_drafts` 表上查詢。supervisor 的提示詞只把 `cases`、`users` 列為 DB_Expert 的範圍，日誌中 agent 查欄位時也只查了 `cases`、`users`、`categories`。這題的耗時仍是有效的量測，但答案不可信。

- 第 6 次呼叫結束時，串流時間約 23.06 秒（日誌累計 22.72 秒 ＋ 起始等待 0.34 秒），第 7 次讀取提示 0.23 秒，所以如果答案立刻開始顯示，第一個 delta 應在約 23.3 秒；實際在 27.94 秒，中間約 **4.65 秒**沒有任何顯示。

- 模型確實有思考（經測試者確認），Modelfile 無法關閉，只能在呼叫時設定（見 6.7）。所以這段時間應該就是被解析器濾掉的思考內容。
- 其他 7 次呼叫是否也有思考、各有多少，這份資料無法判斷：8 次呼叫共生成 984 個 token，其中顯示出來的最終答案約 228 個，其餘約 756 個 token 是路由輸出、工具呼叫（SQL）與思考的總和，無法拆開。

### 6.2 做法一：把資料表結構放進 DB_Expert 的提示詞（P2、P3、P4、P5）

在 DB_Expert 的 system prompt 加入下面這段（依你的實際結構調整）：

```text
你可以使用的資料表如下，欄位名稱以此為準，不要查詢 information_schema：

users(account PK, name, is_staff, is_suspended, suspended_at, line_user_id)
categories(categories_id PK, key_name, label, color_code)
cases(cases_id PK, description, category_id → categories.categories_id,
      images JSONB, status ('pending'/'resolved'), created_at BIGINT（13 位毫秒時間戳）,
      author_account → users.account, address, reject_reason)

寫 SQL 的規則：
1. 一次寫出正確的 SELECT，不要先探索資料表結構。
2. 類別中文名稱用 categories.label，關聯用 cases.category_id = categories.categories_id。
3. 時間戳轉日期：to_timestamp(created_at / 1000.0)。
4. 列清單的題目一律加 LIMIT 10，需要總筆數時用 COUNT(*) OVER() 帶出，不要另外再查一次。
5. 只選回答需要的欄位；描述用 LEFT(description, 40)。
6. 查到資料後直接回答，不要再做確認用的查詢。
7. 回答精簡：先講總數，列表最多 5 筆，其餘請使用者追問。
```

注意：目前 supervisor 的提示詞只把 `cases`、`users` 列為 DB_Expert 的範圍。如果希望它回答事件草稿的問題，要把 `event_drafts` 加進範圍並寫進上面的結構，否則 DB13、DB14 這類問題會在錯誤的表上查詢。

### 6.3 做法二：改 SQL 本身（P3）

目前 agent 實際執行的 SQL：

```sql
SELECT c.cases_id, c.description, c.status, c.address, c.created_at, cat.label AS category_name
FROM cases c LEFT JOIN categories cat ON c.category_id = cat.categories_id
WHERE c.author_account = 'test1' ORDER BY c.created_at DESC;
```

建議改成這樣（這條我沒有在你的資料庫上執行過，請先在 `psql` 跑一次確認欄位和語法）：

```sql
SELECT cat.label AS category, c.status,
       to_char(to_timestamp(c.created_at / 1000.0), 'MM-DD') AS created,
       LEFT(c.description, 40) AS description,
       COUNT(*) OVER() AS total
FROM cases c LEFT JOIN categories cat ON c.category_id = cat.categories_id
WHERE c.author_account = 'test1'
ORDER BY c.created_at DESC
LIMIT 10;
```

預期每列約 40 個 token，10 列約 400～500 個 token（估計），比原本的 5365 個少一個數量級。

### 6.4 做法三：在工具層加保護（P3）

不管模型寫出什麼 SQL，工具在把結果交給模型前先截斷。下面是通用寫法，要依你實際的資料庫工具調整：

```python
MAX_ROWS = 20
MAX_CELL = 60

def _cut(v, n=MAX_CELL):
    s = str(v)
    return s if len(s) <= n else s[:n] + "…"

def format_result(columns, rows):
    lines = [" | ".join(columns)]
    for row in rows[:MAX_ROWS]:
        lines.append(" | ".join(_cut(v) for v in row))
    if len(rows) > MAX_ROWS:
        lines.append(f"（共 {len(rows)} 筆，只顯示前 {MAX_ROWS} 筆；需要更多請縮小條件）")
    return "\n".join(lines)
```

最後那行提示很重要，讓模型知道結果被截斷了，不會誤以為那就是全部。

### 6.5 做法四：supervisor 路由（P6）

- **先看這 110 個 token 是什麼**：在 `supervisor_node` 裡暫時印出 `routed["raw"].content`（或對應的原始輸出）。目前用 `with_structured_output(RouteResponse, include_raw=True)` 並加了「請先列出 plan」的指示，如果 `RouteResponse` 除了 `plan`、`next` 還有說明或理由欄位，輸出就會變長。思考已確認開啟，這 110 個 token 也可能包含思考內容。
- **精簡輸出**：`plan` 只輸出專家名稱，不需要說明文字；`next` 用固定選項。
- **（可選）給路由用較小的模型**：為 supervisor 另建一個 `ChatOllama`，使用較小的模型（例如 qwen3.5:9b，一般生成速度較快，實際倍數與對這個 agent 的影響需要實測）。但這需要另外驗證路由與寫 SQL 的正確率。
- **不建議**「所有計畫中的專家都回報完就直接跳過收尾那次 LLM 呼叫」：只省約 0.4 秒，而且會失去程式註解中說明的「中途補派專家」功能。

### 6.6 做法五：Web 路徑（P7）

1. 用 `stream_probe.py` 對 WEB02（最快，25 秒）和 WEB20（最慢，87 秒）各跑 2～3 次，看時間落在路由、搜尋還是輸出。
2. 對照 Ollama 日誌，數出每次請求的模型呼叫次數，以及回覆讀取了多少搜尋結果（提示 token 數）。
3. 如果搜尋結果很長，限制搜尋次數與結果數量（例如 Tavily 的 `max_results`、`search_depth` 參數，若你使用的是這些參數）、截斷每筆內容，並要求精簡回答。

### 6.7 做法六：在呼叫時關閉思考（P10）

Modelfile 無法設定關閉思考，只能在呼叫時設定。

**Ollama API**：請求的最外層加 `"think": false`（與 `model`、`messages` 同一層，不是放在 `options` 裡）：

```json
{"model": "qwen3.8-16k:latest", "messages": [...], "think": false, "stream": false}
```

**agent 程式**：agent 使用 `ChatOllama`。如果是 `langchain-ollama`，通常用 `reasoning=False`（對應 Ollama 的 `think: false`）；參數名稱依實際版本為準，請查對應版本的文件。supervisor 與各專家如果各自建立了 `ChatOllama`，每一個都要設定。

**怎麼確認有生效**：

- 重跑 DB07（用 `stream_probe.py`），最終答案那次呼叫的第一個 delta 應該緊接在讀取提示之後出現（目前晚了約 4.65 秒）。
- Ollama 日誌中，第 7 次呼叫的輸出 token 數應從 411 降到接近顯示出來的答案長度（目前顯示的部分約 228 個 token）。

**取捨**：思考模式有時能提高 SQL 與路由的正確率，關閉後請用同一組題目重測，並抽查答案（特別是 DB03、DB06、DB09、DB17、DB18 這類需要計算或換算的題目）。

### 6.8 做法七：常駐時間與並發（P11、P12、P13）

**延長模型常駐時間**（Ollama 預設閒置 5 分鐘後卸載）。用 systemd 設定環境變數：

```bash
sudo systemctl edit ollama
# 在開啟的編輯器加入：
# [Service]
# Environment="OLLAMA_KEEP_ALIVE=30m"
sudo systemctl restart ollama
ollama ps    # 載入後看 UNTIL 欄位
```

代價是模型會一直占用約 16 GiB 的 VRAM，請確認其他程式（例如同一張 GPU 上的語音辨識）用不到這些記憶體。

**並發實測**：日誌顯示模型一次只處理 1 個請求，所以多人同時使用時，後面的請求要等前面的跑完。建議在 `bench_agent.py` 加上並發模式（同時送出 N 個請求，記錄每個請求的耗時），測 1、2、4 個並發，預期第 N 個請求的耗時接近 N 倍的單次耗時（這是依日誌推測，尚未實測）。

## 8. 限制

- Web 組每題只有 1 次，看不出單題的波動；P90 / P95 沒有統計意義；DB 與 Web 的差異同時包含題目本身的影響。
- 只測了單一請求依序執行，沒有並發；日誌顯示模型一次只能處理 1 個請求，多人同時使用時耗時會更長（尚未實測）。
- 只在一個時段（凌晨）測，其他時段伺服器負載不同時數字可能不同；測試時 GPU 上另有其他程式占用約 6.5 GiB VRAM，其運算負載對速度的影響未知。
- 資料量目前很小（66 筆案件），耗時會隨資料量成長。
- 階段拆解與日誌診斷只看了 1 次請求（DB07，8 次模型呼叫，且包含模型重載）；其他題目是否走同樣的路徑，還需要驗證。
- 估計的節省秒數是依單次日誌推算，彼此有重疊，不是預測值。
- 隱藏輸出（約 4.65 秒、約 186 個 token）是依時間推算的，沒有直接看到那些 token 的內容；「是思考內容」依據測試者的確認。其他呼叫的思考量無法從資料判斷。
- 日誌中觀察到的生成速度約 40～42 token/秒；原因不明的是它是否受上下文長度、取樣設定或 GPU 上其他負載影響，這份資料分不出來。
- DB13 的答案可能不正確，詳見 3.2。
- 測試完成後請把 PostgreSQL 的日誌設定改回來：

  ```bash
  sudo -u postgres psql -c "ALTER SYSTEM RESET log_min_duration_statement;" -c "SELECT pg_reload_conf();"
  ```
